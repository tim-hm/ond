## Cross-Cutting Concerns

### Root cause: the identity model's premise expired when `account` landed, and only `merge` noticed

Four findings — [SEC-001], [SEC-002], [SEC-003], [SEC-006] — are one story. "Possession of the id is the whole claim" was a sound trade when the id guarded anonymous, recoverable, low-stakes data. The window added three things that change the stakes without revisiting the trade: a real credential binding (`users.apple_user_id`), an irreversible operation (`DeleteAccount`), and a UI affordance that invites the person to paste the id into an email ([SEC-001]). `merge` is the proof the asymmetry is already understood — it refuses to let the anonymous id outweigh an Apple binding — but `delete_account` applies the old rule to the new world, and the logs record the credential verbatim on every request line. The fix is not a new auth system; it is applying `merge`'s judgement consistently: derived references where the id would be exported ([SEC-001], [SEC-006]), the existing Apple verifier where the operation is irreversible ([SEC-002]), and state that survives erasure where the id anchors an obligation to Apple rather than to the user ([SEC-003]).

### Root cause: new iOS features copied the UI-state pattern, not the logging pattern

[OBS-001] through [OBS-004] are the same defect in four places, all new this window: Sign in with Apple, account deletion, the whole authored-exercise flow, notification scheduling, and the HealthKit write each catch their failures into transient UI state (or a `try?`) with no log line. The backend's newest features shipped with proper `errors.rs` files because the pattern is structural there; the Swift side's convention lives in a doc table that the newest features never joined ([OBS-007] — `account` and `discreet-spike` categories are undocumented, `user-technique` doesn't exist). One pass adds the three missing loggers and trues up the table.

### Systemic: documentation lag is now a wave-following pattern, not a backlog

Yesterday's audit found docs describing the bootstrap; today's finds docs describing last week — a much better problem, but the same shape. [ARCH-001] (architecture.md's identity narrative says nothing writes `apple_user_id`), [ARCH-002] (transport.md's "the one streaming RPC" missed `Chat`), [ARCH-006] (the feature table lists five of seven features; `throttle.rs` is invisible), [OBS-006] (three well-reasoned audit-trail `info` lines in services the observability doc forbids from speaking), and [ARCH-007] (the audit skill itself asserts a stale env-var count) all expired within the fortnight. The "not yet" claims and singular nouns are the recurring failure mode — each names a condition one feature can silently invalidate.

### Contradiction resolved: the seam-module `mod.rs` pattern loses to the documented rule

ARCH and QUAL both flagged trait seams living in `mod.rs` (four files, up to 293 lines) against code-structure.md's "declarations and re-exports only, ~50 lines" rule, and both offered "or amend the doc" as an out. Resolution: the doc wins. The rule's value is that opening `mod.rs` teaches the module's shape, and a 293-line `mod.rs` holding the trait, six types, and a factory demonstrably doesn't. Extract per [QUAL-001]; do not amend the convention.

### Cross-language drift: one contract, two enforcement standards — again

Yesterday's audit flagged the Swift side as the looser end of the shared contract; today's instances are new but the shape recurs. [TYPE-001]: Rust refuses an unknown passage, Swift defaults it onto `.nose` — and the composer round-trip makes the default self-persisting. [TYPE-003]: `technique::positive_count` documents why corrupt rows must fail the call, while `user_technique` — converting the same shapes one feature over — serves them through `unsigned_abs()`. Both are one-sided fixes on two-sided boundaries; both fixes are mechanical because the stricter twin already exists to copy.

### Growth curve: the journey surface is bounded server-side and unbounded client-side

The server now pages, snapshots, and indexes everything per-person — verified. The remaining "slower every day you use it" curves are all in the app: the history strip renders every session ever recorded through a non-recycling `LazyVStack` ([PERF-001]), every consumer re-decodes the whole sessions file per appearance and pretty-prints every rewrite ([PERF-002]), and each restore page recomputes three aggregates the client discards ([PERF-003]). None hurts today; all cross their thresholds silently.

#### Warnings — Type Safety & Robustness

### [TYPE-001] `Passage` decode defaults `UNRECOGNIZED` onto `.nose`, and the composer's edit round-trip makes the default self-persisting

- **Severity:** Warning
- **Location:** `ios/Packages/OndCore/Sources/OndKit/TechniqueRepository.swift:168-180` (the `?? .nose` at line 176)
- **Issue:** `Phase.init(proto:)` decodes `through: Passage(proto: proto.passage) ?? .nose`. `Passage.init?(proto:)` correctly returns nil for both `.unspecified` and `.UNRECOGNIZED`, but the call site coalesces both onto `.nose` — the one place in either language where a proto value the app cannot represent becomes a real domain case instead of a `malformedResponse`. The leniency is defensible for `.unspecified` only; the Rust inbound direction (`passage_from_proto`, `crates/api/src/features/technique/service.rs:232`) refuses exactly this value.
- **Impact:** (1) A future catalogue passage renders on older builds as nose breathing — a wrong instruction presented as fact. (2) Worse: authored techniques route through the same decoder (`Technique(authored:)` in `UserTechniqueRepository.swift:158`), and `TechniqueDraft(editing:)` rebuilds from the decoded value — so an older app opening an exercise composed on a newer app decodes the unknown passage as `.nose`, and saving the edit silently rewrites the stored passage server-side. The default doesn't just mislabel; it overwrites the person's data.
- **Action:** Split the two cases the enum already distinguishes: keep the lenient degrade for `.unspecified` (or only reach the passage when `kind` is a breathing kind, mirroring the oneof shape), and throw `TechniqueRepositoryError.malformedResponse` for `.UNRECOGNIZED` — the rule every other enum on this boundary follows.

### [TYPE-002] Stream ending without a terminal `.complete` finishes cleanly — the exact "stopped vs finished" ambiguity the wrapper exists to prevent

- **Severity:** Warning
- **Location:** `ios/Packages/OndCore/Sources/OndKit/AssistantRepository.swift:186-189`
- **Issue:** `bridged(_:request:chunk:)` correctly throws when a terminal `.complete` carries a non-OK code, but when `stream.results()` runs dry without any `.complete`, the fallthrough calls `continuation.finish()` — a clean end. The reader-cancellation path never reaches this line live (after `onTermination` fires, `finish()` is a no-op), so the only live path here is the abnormal one.
- **Impact:** `docs/transport.md`'s own hazard: a stream that simply stops is indistinguishable from a short answer. If Connect ever ends `results()` without a terminal message, the coach UI captions a truncated answer as the whole of it, silently. This is the one gap in an otherwise airtight wrapper shared by all three streaming RPCs.
- **Action:** Replace the bare `continuation.finish()` at line 189 with `continuation.finish(throwing: AssistantRepositoryError.transport("the stream ended without a status"))`. On the already-terminated cancellation path this is a no-op, so nothing regresses.

### [TYPE-003] `user_technique` serves database rows through `unsigned_abs()` — the silent rewrite the sibling feature's `positive_count` was written to refuse

- **Severity:** Warning
- **Location:** `crates/api/src/features/user_technique/service.rs:390` (`rounds.unsigned_abs()`), `:365` (`cycles`), `:404-424` (`phase_to_proto`: `duration_ms`/`min`/`max`)
- **Issue:** `technique::service::positive_count` (`technique/service.rs:191-197`) narrows the catalogue's CHECK-constrained positive columns fallibly, and its doc names the alternative explicitly: "`unsigned_abs` would surface `-4000` to a client as `4000`". The user-technique feature, converting the same shapes from equally CHECK-constrained columns (`0012_user_techniques.sql`), does exactly the rewrite that doc forbids on its read/list path. The write paths (over an in-memory validated draft) are fine.
- **Impact:** A corrupt row (bad restore, future migration slip) is served as a plausible positive number instead of failing as `Inconsistent` — indistinguishable from a value the person authored, and inconsistent with the standard the codebase documents one feature over. `docs/testing.md`'s "a corrupt row must fail the call" names this shape.
- **Action:** On the read path, narrow with a fallible conversion returning `UserTechniqueError::Inconsistent` (reuse or mirror `positive_count`) for `rounds`, `cycles`, and the three duration fields. Keep `unsigned_abs()` only where the value is provably validated in-memory this request.

### [PERF-002] Every consumer re-decodes the whole sessions file per appearance; pretty-printed JSON doubles the cost of every rewrite

### Security & Hygiene

#### Critical — Security & Hygiene

### [SEC-001] The Settings "Support ID" row exports the caller's whole bearer credential

- **Severity:** Critical
- **Location:** `ios/Ond/Features/Settings/SupportIdentifierRow.swift:26-52`, `ios/Ond/Features/Settings/AccountSection.swift:71-78`
- **Issue:** The row renders the full anonymous UUID and copies it to the system pasteboard on tap, labelled "Support ID" — an invitation to paste it into an email, a screenshot, or a support thread. Under this identity model that UUID is not an identifier, it is the credential: anyone who presents it in the `ond-user-id` header owns the record — reads and rewrites the profile, reads the journey, spends the assistant quota, and (via `DeleteAccountRequest`, which takes nothing but the header) irreversibly erases the account. The design rule is explicit that the id must never be embedded in something exportable; this is exactly that shape, built deliberately.
- **Impact:** Every support interaction that uses this row moves a full-control bearer token into an uncontrolled channel (mail provider, screenshots, clipboard managers, third-party keyboards). One leaked "Support ID" is silent, total account takeover including destruction — and the person leaked it because the UI told them that is what the id is for.
- **Action:** Never surface the raw id. Give support a derived reference instead: a UUID prefix (8–12 hex chars finds a row with `LIKE`), or a server-minted `support_reference` that carries no authority. If the full id must remain visible, pair it with credential hygiene: rotate the id after a support contact, or gate destructive RPCs behind more than the header ([SEC-002]).

#### Warnings — Security & Hygiene

### [SEC-002] `DeleteAccount` erases an Apple-bound account on the strength of the anonymous id alone

- **Severity:** Warning
- **Location:** `crates/api/src/features/account/handlers/grpc.rs:52-58`, `crates/api/src/features/account/service.rs:57-69`
- **Issue:** "Possession is the claim" is the accepted V1 trade for anonymous rows — but `features/account` exists precisely because a stronger credential now attaches. `merge` already honours the asymmetry: it refuses to fold away a bound row because possession of an anonymous id "is not a credential this may weigh against a signed-in one." `delete_account` does not — the same UUID that cannot fold a bound row away can destroy it outright, along with everything the Apple credential was supposed to make recoverable.
- **Impact:** The one irreversible operation in the API is gated on the weakest credential in the system, even where a stronger one exists and is checked elsewhere for a less destructive operation. Combined with [SEC-001], a leaked Support ID becomes unrecoverable erasure of a signed-in customer's history.
- **Action:** When the caller's row carries an `apple_user_id`, require a fresh Apple identity token in `DeleteAccountRequest` and verify its `sub` matches the binding (the verifier already exists in `account/verifier/apple.rs`). Anonymous rows keep the current behaviour — the header is genuinely all they have.

### [SEC-003] A refund's finality does not survive `DeleteAccount` — the tombstone dies with the row

- **Severity:** Warning
- **Location:** `crates/api/src/features/account/repository.rs:41-47`, `crates/api/src/features/entitlement/service.rs:77-132`
- **Issue:** The refund-replay fix (pinned by `a_refund_cannot_be_undone_by_resubmitting`) works because the revoked row keeps `subscription_signed_at` and the binding. Both defences live on the `users` row. `delete_account` deletes that row, releasing `app_store_original_transaction_id` entirely — so a refunded subscriber can tap Delete account, let the client mint a fresh UUID, and resubmit the pre-refund `jwsRepresentation` (which verifies forever — its payload carries no `revocationDate`). `find_transaction_holder` returns `None`, and the refunded tier is restored until its original `expires_at`.
- **Impact:** The property yesterday's critical was fixed to establish — "a refund is final" — is escapable via an in-app button plus a reinstall. Bounded (only until the refunded period's expiry, spend capped at 50 calls/day), but it converts a pinned invariant into one that only holds for accounts never deleted.
- **Action:** Persist revocations outside the row they revoke: a `revoked_transactions(original_transaction_id primary key, revoked_at)` table written in `revoke` and consulted at the top of `claim` survives both `delete_account` and `merge`, costs one indexed lookup on the purchase path, and does not complicate erasure. Add an e2e sibling to the replay test that interposes a `DeleteAccount`.

### [SEC-004] A live OpenRouter API key lingers in `.env` for a provider the codebase no longer uses

- **Severity:** Warning
- **Location:** `.env:1`
- **Issue:** `.env` (gitignored, correctly untracked) still carries `OPENROUTER_API_KEY=sk-or-v1-…` — a real-shaped secret for the provider replaced by Bedrock when `openrouter.rs` was deleted. The project's own contract says `.env` holds only machine-local iOS release values, and that any server-side variable appearing there is itself the finding. `.mise.toml` loads the file into the environment of every mise task and child process.
- **Impact:** A spendable credential nobody remembers exists, injected into every build, test, and deploy process. It leaks into any tool that dumps its environment, and the key remains valid at OpenRouter until revoked — the integration it belongs to has no owner any more.
- **Action:** Revoke the key in the OpenRouter dashboard, then delete the line. Nothing in the repo reads it. Check `docs/contributing.md`'s `.env` enumeration mentions only current values.
- **Cross-referenced by:** QUAL

### [SEC-005] The advisory watch exists but cannot run: GitHub Actions are disabled and `check:audit` is outside every local chain

- **Severity:** Warning
- **Location:** `.github/workflows/audit.yml`, `.mise.toml:465-476`
- **Issue:** The previous audit's standing finding was answered structurally — `cargo-audit` is pinned, `check:audit` exists, and `audit.yml` schedules it nightly. But Actions are disabled for the repo, so both workflows are dead files, and `check:audit` is deliberately excluded from `mise run check` (defensibly: it needs the network and fails on the calendar). The net effect is unchanged: nobody runs the advisory check. #### Suggestions — Security & Hygiene

### [SEC-006] Every request log record carries the caller's full bearer credential

- **Severity:** Suggestion
- **Location:** `crates/api/src/obs.rs:142-144`, `crates/api/src/identity.rs:86-95`
- **Issue:** `identity::resolve` declines to log a malformed header value because "it is the caller's whole credential" — and then records every valid one verbatim onto the request span, from where it lands in the production JSON stream on every completed-request line. The same reasoning applies to both: a valid id is more of a credential, not less. Attribution is the stated purpose, but attribution does not need the spendable form.
- **Impact:** The log stream (and its backups, and anything it is copied into during debugging) is a flat file of full-control bearer tokens for the entire user base. Log access today equals box access, but logs travel further than databases do.
- **Action:** Record a stable derivation — the first 8–12 hex chars of the UUID, or a keyed hash. Cross-request correlation and support lookups survive; the credential does not. This composes with [SEC-001]: a truncated log id and a truncated Support ID can be the same value.
